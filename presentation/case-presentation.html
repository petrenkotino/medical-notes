Medical Notes API

Design, load testing, and one improvement

Node.js, TypeScript, Fastify, and PostgreSQL

Tino Petrenko · September 2026
Application overview

What I built

API

Node.js 24, TypeScript, and Fastify. Three endpoints to create, read, and update medical notes.

Database

PostgreSQL 17 through Postgres.js. Note history is stored as immutable versions.

Local setup

Docker Compose, persistent database volume, request schemas, health, and readiness endpoints.

For the load tests the API ran directly on the host for easier resource sampling. PostgreSQL remained in Docker, so this was still a mixed host/container setup.
Data model

Note versions and concurrent updates

PRIMARY KEY (id, version)

Every edit is a new row. PUT reads the current version and inserts the next one in a single statement.

Writer A
next = 5
Writer B
next = 5
→
one 200
one 409

Current behavior

  • No duplicate persisted versions
  • No silent overwrite
  • Complete revision history
  • Works across Node processes
This keeps the stored data consistent. A real product still has to decide whether a stale edit should be rejected, retried, or serialized.
Correctness

What I tested before running load

Acceptance tests

  • POST → GET → PUT → GET
  • Response fields and version increments
  • Invalid UUIDs and request bodies
  • Missing notes

Concurrent updates

  • Five updates sent to the same note
  • Successful writes have unique versions
  • Conflicting writes return 409
  • No unexpected 500 responses

I also checked manually that a note survives a service restart.

Bottleneck investigation

Testing the pool-size hypothesis

PostgreSQL sampling

Interpretation

Trade-offs, assumptions, and limits

Trade-offs I made

  • Append-only versions preserve history, but use more storage and leave stale-edit handling unresolved.
  • 409 prevents a silent overwrite, but still represents unsuccessful work for the user.
  • Pool 40 favored throughput. Pool 30 had lower latency, fewer conflicts, and used fewer connections.
  • The closed-loop workload finds saturation quickly, but is not representative user behavior.

What limits the result

  • Small payloads, 50 hot notes, fixed 70/20/10 traffic, and no think time.
  • API, k6, and Dockerized PostgreSQL ran on one machine; there was no TLS, ingress, or authentication.
  • Most configurations have one 60-second measured run, so small differences may be noise.
  • One-second PostgreSQL samples can miss millisecond contention; pool wait and event-loop lag were not measured.
  • Throughput includes expected 409s, so it is not identical to successful business work.
The tests support a relative claim about this local setup. They do not establish production capacity, an exact saturation boundary, or a number of real users.

Capacity

What the test says

25 VUs at about 10,300 req/s was the highest tested point before degradation with one process and pool 40.

At 50 VUs, throughput was effectively flat while latency doubled. That is the first observed degradation point in the improved series.

At every tested level, unexpected infrastructure failures remained zero.

Test boundaries

  • Small, fixed payloads
  • 50 cache-friendly notes
  • Local network
  • No TLS, authentication, or reverse proxy
Next improvements

What I would do next

  1. Repeat the one-, two-, and four-process tests while keeping the total database connection limit fixed.
  2. Measure pool wait time, event-loop lag, query duration, PostgreSQL waits, and each process separately.
  3. Decide what should happen when two users update the same note before adding automatic retries.
  4. Add request and query timeouts, bound pool waits, drain connections on shutdown, and test database failures.
  5. Repeat with realistic note sizes and traffic, separate hosts, and an arrival-rate target tied to an actual latency objective.

Appendix

Update conflicts

Ten percent of workload requests update one of only 50 seeded notes. Larger pools and more workers allow more of those updates to reach PostgreSQL concurrently.

A 409 is an expected, correctness-preserving response in this design. It is still unsuccessful business work and must not disappear inside aggregate throughput.
~16%
estimated PUT conflict share in the two-worker 200-VU experiment

This is why the next step is to define edit semantics before adding retries or serialization.

Appendix

Decisions made for this exercise

Authentication

authorId is attribution supplied by the client, not verified identity.

Production topology

No ingress, TLS, separate hosts, autoscaling, or managed database.

Product semantics

No decision yet on stale-edit reconciliation, idempotency, retention, or deletion.

These are scope decisions for the take-home, not suggested production defaults.
